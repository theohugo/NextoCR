# NextoCR roadmap

NextoCR's goal is a reproducible self-play research stack, not merely an agent that can launch a
match. Each phase therefore has measurable exit criteria. Later phases must not hide simulator or
evaluation weaknesses discovered earlier.

## Phase 0 — Adopt and freeze the simulator baseline

Status: **in progress**

The project is based on the Apache-2.0
[`voonhous/crforge`](https://github.com/voonhous/crforge) engine so that work starts from a tested,
data-driven simulator rather than a mock Gym wrapper or a new physics implementation.

Deliverables:

- [x] Preserve upstream history, license, and NOTICE in the public standalone `NextoCR` repository,
      originally created as a fork of `crforge`.
- [x] Verify the complete Gradle build on Java 17.
- [x] Document architecture, source selection, data provenance, and legal scope.
- [x] Add a dependency-free card catalog audit.
- [x] Fix world-local entity ID allocation so parallel environments cannot corrupt one another.
- [x] Inject and reset the engine targeting and built-in opponent random streams from the episode
      seed.
- [x] Make action acceptance explicit; do not infer it from pre-tick elixir deltas.
- [ ] Add deterministic replay hashes that cover the complete observable state, not only the hand.
- [x] Publish an initial single-env and multi-env throughput smoke baseline with hardware and
      command lines; repeat it on the final commit for release-quality numbers.

Exit criteria:

- `./gradlew clean build` passes.
- Catalog audit passes in strict mode.
- Two isolated sessions may reset and step concurrently without shared mutable simulation state.
- Replaying the same action trace with the same seed produces the same state hashes.
- A different seed affects only explicitly stochastic decisions.

## Phase 1 — Fidelity and complete competitive card coverage

Status: **started by the inherited engine; not complete**

The current tracker reports 112 entries as done, six partial, and ten missing. Raw JSON also
contains evolution and alternate-mode definitions that should not be confused with implemented
mechanics.

Deliverables:

- [ ] Convert the human tracker into a versioned machine-readable implementation manifest.
- [ ] Record a source, balance version, confidence, and validation method for every gameplay field.
- [ ] Implement the four missing non-default Tower Troops.
- [ ] Complete all champion abilities and their action/observation representation.
- [ ] Implement evolutions as mechanics, not only alternate stat records.
- [ ] Reconcile the catalog with the current official card list and flag additions automatically.
- [ ] Build golden interaction tests for damage, first hit, range, targeting, movement, spawns,
      spells, tower activation, and overtime.
- [ ] Quantify known approximations instead of describing the simulator as frame-perfect.

Exit criteria:

- Every currently competitive card is `DONE` or explicitly excluded with a reason.
- Every implemented card has at least one isolated mechanic test and one integration interaction.
- Catalog snapshots identify their balance season/date and pass reference/schema checks.
- A published fidelity report compares a representative interaction suite with observed game
  outcomes.

## Phase 2 — High-throughput RL environment

Status: **schemas and identity landed; throughput work outstanding**

The inherited project already provides binary observations, action masking, JPype, and a threaded
vector environment. This phase turns those prototypes into a measured training substrate.

Deliverables:

- [x] Version the action and observation schemas (`exact_discrete_v1`, `nextocr_static_v1`); a run
      refuses to resume if either changed.
- [x] Encode a stable unit/card identity per entity; generic troop/building type is insufficient
      for learning card-specific interactions.
- [ ] Support exact tile placement as well as configurable strategic-zone abstractions.
- [ ] Expose legal-action masks generated by the engine, including abilities and special cards.
- [ ] Remove fixed-size observation truncation or make overflow observable and tested.
- [ ] Benchmark 1/8/32/128 environments and identify contention, allocation, and GC costs.
- [ ] Add headless batch evaluation that does not depend on Stable-Baselines3.
- [ ] Save and restore complete simulator state for curriculum and counterfactual rollouts.

Exit criteria:

- Gymnasium's checker passes for every supported backend and observation mode.
- ZMQ and JPype produce equivalent state/reward traces for the same seed and actions.
- Vector throughput scales without cross-session races or nondeterministic corruption.
- Training configs include schema, simulator commit, data snapshot, seed set, and hardware metadata.

## Phase 3 — Self-play league

Status: **bounded league training; ratings and promotion gates outstanding**

Replacing the opponent with the latest checkpoint is not enough: it encourages forgetting and can
produce misleading win-rate curves.

Deliverables:

- [ ] Immutable checkpoint registry with metadata and hashes. Metadata is recorded per checkpoint;
      content hashes are not.
- [ ] Opponent sampling from recent, historical, exploitative, and scripted populations. Recent,
      historical and scripted are in use; exploiters are not implemented.
- [ ] Elo/TrueSkill-style ratings based on fixed evaluation matches, not training rollouts.
- [ ] Held-out decks, seeds, scripted scenarios, and exploiters.
- [ ] Promotion gates before a checkpoint joins the main population.
- [ ] Recurrent and attention-policy baselines alongside a small MLP baseline.
- [ ] Curriculum over decks, action granularity, card pool, and match phases.

Exit criteria:

- Results reproduce across at least three seed sets.
- A promoted policy beats the previous league champion and held-out baselines under a predeclared
  evaluation protocol.
- Performance is reported by deck/matchup/scenario, not only aggregate reward.

## Phase 4 — Scale and reproducibility

Status: **single-machine runs are resumable and manifested; scale-out not started**

Deliverables:

- [ ] Worker/learner architecture for one machine, then multiple machines if justified by profiles.
- [x] Fault-tolerant rollout collection and checkpoint resumption, including a checkpoint written
      on crash or interruption and resume from the exact step reached.
- [x] Experiment manifests, metrics, artifacts, and deterministic evaluation jobs.
- [ ] CPU, memory, and wall-clock budgets for every published run.
- [ ] Public small baseline checkpoints that can be reproduced without a cluster.

Exit criteria:

- An interrupted run resumes without changing its declared experiment identity.
- A clean machine can reproduce the baseline from one documented command and config.

## Phase 5 — Visual validation, not live automation

KataCR is useful for perception research and comparing simulated state with recorded gameplay. The
current repository deliberately excludes control of the official game client.

Possible research, subject to a separate policy and legal review:

- offline replay/video state extraction;
- simulator-versus-video interaction comparison;
- calibration of uncertain movement, targeting, and timing parameters;
- domain-gap measurement between synthetic and recorded observations.

Out of scope here:

- controlling a live account;
- bypassing anti-cheat or platform restrictions;
- private servers or modified clients;
- distributing official game assets or binaries.

## Research principles

1. **Fidelity before scale.** Millions of biased games produce a confidently wrong policy.
2. **Evaluation before claims.** Training reward is not skill.
3. **Version every interface and dataset.** A checkpoint without its simulator/data version is not
   a reproducible artifact.
4. **Keep engine and policy separable.** The simulator must remain useful to algorithms other than
   PPO.
5. **Prefer measured facts to undocumented constants.** Attach confidence and evidence when exact
   values are unavailable.
